# elrsd — ExpressLRS 2.4 GHz sniffer / bench transmitter

RX-first ExpressLRS 3.3.1 daemon for the RFNM Blue: one 25 MSps capture over the librfnm
local transport, a burst-gated LoRa front end (SF5–SF8 with the SX1280 long interleaver),
FHSS tracking from the binding phrase, RC/SYNC packet decode, and a small HTTP/JSON API
with a web-GUI panel. A TX path (same frames, positional `tx_stream`) is built in but
**off by default**: it only transmits when the board policy, a start flag and a runtime
arm request all agree, and it auto-disarms.

Rates (3.3.1 OTA4, 8-byte packets): `500hz` SF5 CR4/6, `250hz` SF6 CR4/8, `150hz` SF7
CR4/8, `50hz` SF8 CR4/8 (hop every 2 packets) — all four verified bit-exact on the
2026-09-14 captures. OTA8 rates (333/100 Hz) are unsupported and refused.

## Signal chain

```
RFNM RX ch0 (25 MSps cs16) ──► capture thread ──► bounded queue ──► DSP thread
                                                                    │ int16 envelope (125 µs blocks)
                                                                    │ burst cut from a 60 ms raw ring
                                                                    │ channel estimate (FFT centroid on the 1 MHz grid)
                                                                    │ mix + polyphase resample (13/100 → 3.25 MSps)
                                                                    │ CSS demod + frame sync → raw symbols + ref
                                                                    ▼
                                    rx_tracker: LI decode → CRC-14 (UID) → link model (slot clock, Lock B from
                                    the FHSS sequence fit on RC packets, Lock A from SYNC packets) → packet ring,
                                    link stats, channel hint back to the front end
```

The window is 25 of the 80 channels (channel *i* at 2400.4 + *i* MHz). The default centre
2441.4 MHz covers channels 29..53 including the SYNC channel 41, so a full lock (absolute
nonce) is possible; the other manifest choices are 2412.4 MHz (0..24) and 2466.4 MHz
(54..78). Bursts on channels outside the window are simply not seen — the status reports
them as `slots_missed`. Without a SYNC packet the lock is `mod_hop` (dwell phase and
channel sequence known, nonce only modulo the hop interval), in which case the aux-switch
slot of RC packets is ambiguous and reported as `-1`.

## Binding phrase / UID

The UID (6 bytes derived from the binding phrase exactly as the ELRS firmware does) is
needed for the FHSS sequence and the packet CRC. It is **runtime configuration only**:
`PUT /config {"binding_phrase":"..."}` (the panel has a password field for it) or the
environment variable `ELRS_BINDING_PHRASE` / `ELRS_UID`, which the daemon removes from its
environment right after reading. It is never a command-line flag, never logged, never in
`/status`. The tree only contains a TEST-UID for the selftest vectors.

## HTTP API

JSON over HTTP on `127.0.0.1:7694`, published by the on-board nginx as `/api/app/elrs/`
(route generated by appd from the manifest). `GET /api` lists the routes.

| route | what |
|---|---|
| `GET /status` | state (`idle` / `listening` / `tx_armed`), rate, `uid_set`, `rx` (source, window, drops, floor, cpu), `fhss` (lock, slot, nonce + confidence, pointer, channel, next sync slot), `counters` (bursts, decoded, crc ok/fail, rc/sync, slots expected/missed, packet rate, LQ, SNR/RSSI), last `rc`, `tx` |
| `GET /packets?since=SEQ&max=N` | decoded packet ring (500), newest last: slot, channel (+ predicted), kind, crc, nonce, 16 CRSF channels, switch index, hex, ground-truth flag in replay |
| `GET /rc` | last CRC-ok RC packet (16 CRSF values, arm bit, aux slot) + link quality |
| `GET /channels` | bursts per channel (80), last-seen times, window, predicted next channels |
| `PUT /config` | `{"binding_phrase":"..."}` or `{"uid":"d2:4c:.."}`, optional `"rate"`, `"conj"`, `"fc_hz"` |
| `GET /tx/status` | TX state, policy, power applied/cap/range, LO, counters, retune percentiles, adapter health |
| `POST /tx/arm` | `{"power_dbm":-30,"antenna":"sma_a","duration_s":30,"max_bursts":0,"rate":"250hz","sync_packets":true}` |
| `POST /tx/disarm` | stop transmitting, restart RX |
| `POST /tx/rc` | `{"ch":[16 CRSF values 172..1811]}` — the RC values to transmit |

Errors are `{"err":"..."}` with 400 (body), 403 (board policy) or 409 (state/gate).
Optional WebSocket push (`--ws-port N`, loopback): `{"type":"packet"|"rc"|"status",...}`.

## TX safety model

TX is armed only when **all** gates pass, and the librfnm adapter checks the first three
again by itself before any write:

1. `/rfnm/board.conf` `TX_ALLOWED` — absent/`0` = no TX object exists at all (403 on arm);
   `embed` = embedded antenna only (a board without it refuses, never falls back); `1` = any path.
2. the daemon was started with `--tx 1` (`ELRS_ARGS` in `elrs.conf`; default off).
3. `POST /tx/arm` with `power_dbm` ≤ the cap (`--tx-cap-dbm`, default −20 dBm) and a
   duration ≤ 120 s; auto-disarm afterwards, `POST /tx/disarm` any time, SIGTERM disarms.

While armed the receiver is stopped (v1: no duplex on this board); `/status.state` is
`tx_armed`, and the TX block of the panel shows the applied path, power and the retune
statistics. The synthesized frames are the ones the receiver decodes (`--loopback`). The one
exception is the hardware self-loop below, which runs TX and RX on the same device at once.
A fifth guard lives in the adapters: a board whose `power_range.min` lies above the cap is
refused rather than clamped up.

## Hardware self-loop (`--selfloop-device`)

A send test that stays on the board: the normal `elrs_transmitter` (FHSS hop, SYNC packets,
RC packets with a fixed deterministic channel pattern) runs through the librfnm adapter on TX
ch0 at the **lowest power the board offers** (`power_range.min`, never above the caps), and
the normal RX source + `rx_chain` + tracker listen on the **chip-internal loopback** of the
Lime card at the same time (`--selfloop-rx-path loopback`, RX path `RFNM_PATH_LOOPBACK`: the
LMS7002M RFE loopback tap on the TXPAD output; the driver's sysfs parser accepts `loopback`
even though the card does not advertise it in `path_possible`). Every TX gate applies
unchanged: `/rfnm/board.conf` `TX_ALLOWED`, `--tx 1`, the runtime cap and the compile-time
hard cap (0 dBm). Order on the device: TX apply first, then the RX apply without parking the
TX (the reverse order leaves the Lime RX deaf).

```sh
# on the board, as root, appd's elrs lease stopped (the daemon must not hold the device):
cd /rfnm/apps/elrs && systemctl stop rfnm-elrs
set -a; . ./secret.env; set +a          # ELRS_BINDING_PHRASE (optional: without it the TEST-UID is used)
./elrsd --selfloop-device 20 --tx 1 --rate 250hz --fc 2441.4e6 --gain 0
# feed diagnostic: no bursts, a continuous tone at LO + 1 MHz through the same feed path, raw RX to a file
./elrsd --selfloop-device 6 --tx 1 --selfloop-cw --rate 250hz --fc 2441.4e6 --fs 50e6 --gain 20 --selfloop-dump /tmp/selfloop_cw.cs16
```

Order on the device (changed after the 2026-09-14 run/ #15): TX RF apply, RX
apply, wait for the first RX block, **then** the TX feed session is anchored (`session_start`);
the feed is continuous (zeros between the bursts, no seeks) and the report carries the feed
counters (`bursts_fed`, `bursts_late`, `packets`, `drops`, `frontier_lead_us`) and the device's
placement counters (`pos_placed`, `pos_late`, `pos_misaligned`, `underruns`, `anchor_moves`,
`rebases`). `--selfloop-cw [OFFSET_HZ]` replaces the bursts with a tone (amplitude 14000, default
+1 MHz from the LO) - a `--selfloop-dump` capture then shows immediately whether baseband reaches
the DAC (`ok` = packets flowed, no drops).

prints one JSON report and exits 0 when **every CRC-ok packet is byte-equal to what the
transmitter sends** (`verify.ok`: `crc_ok > 0`, `mismatch == 0`, `rc_bitexact + sync_bitexact
== crc_ok`), 1 when packets came back wrong or none at all, 2 when refused (no device, policy,
`--tx 0`, arm or RX-apply failure - the refusal is in `err`). The report carries the TX side
(path, applied power, range, LO, bursts sent/dropped, retunes, `slots_in_rx_window` = how many
transmitted slots the 25 MHz RX window could see at all, tx_stream health), the RX side
(bursts, decoded, crc ok/fail, rc/sync, floor, cpu) and the verification counters. The FHSS
lock is reported but not required. Progress goes to stderr every 5 s; SIGINT stops early
(TX RF_OFF first, then RX).

**What can radiate.** The chip tap is non-diverting: the TX still drives the card's SMA_A
connector (the Lime TX has no other path). Run it with **no antenna on SMA_A** (open, or a
50 Ohm load) - then nothing leaves the board; the applied power is in the report. The RX
gain rides the loopback buffer (`--gain 0` is a sane start; negative values only park the
PGA). Whether the deployed kernel module implements the TX-live chip tap or the legacy
factory-cal FE loopback for `rx0 path=loopback` is not measured yet (); an RX apply that the
module rejects ends the run with exit 2 and the apply error. Fallbacks, both explicitly
**not** RF-free on one Lime card: `--selfloop-rx-path embed_ant` (RX on the on-board antenna
hears the TX leakage of a terminated SMA_A - the measured single-card duplex path), and on a
board with two Lime cards `--selfloop-rx-channel 1` with a cable `SMA_A -> >= 30 dB pad ->
second card SMA_A` (the conducted two-card link of 2026-08-28). RX on `sma_a` while TX is on
`sma_a` cannot work (one switch). The verification logic (pattern, byte-equality per nonce,
SYNC timeline consistency, counting, JSON) is host-tested in `--selftest` (tx section); the
device sequence itself is not exercised on the host - `./elrsd --selfloop-device 5 --tx 1`
on the host answers `no device` with exit 2.

## Pure transmit (`--tx-only`) — the send half of the two-board proof

A board-only transmit mode that opens **no RX path at all** (no RFNM RX source, no
`start_rx_locked`, no RX apply). The same normal `elrs_transmitter` runs — FHSS hop, SYNC on
channel-41 visits, RC packets with the fixed deterministic channel pattern — through the librfnm
adapter on TX ch0 at `--tx-only-dbm` (default −100 dBm → the adapter clamps up to `power_range.min`,
never above the caps). A second board receives separately.

Why a separate mode: a two-board send test failed because the daemon was
**receiving while transmitting on the same Lime card**. The concurrent RX apply moves the TX time
axis (`rfnm::tx_stream` latches the anchor once), so the kernel throws away every stamped burst as
"late" (`pos_placed 0`) while the host keeps counting `bursts_sent` — the receiving board
heard only noise. The CW self-loop **without** an RX apply reached `pos_placed 11560`. With no RX
apply the anchor stays put and the samples reach the DAC. So `--tx-only` arms with the feed session
started **immediately** (`arm(start_session=true)`, unlike `--selfloop-device` which defers it to
after the first RX block).

```sh
# on the board, as root, appd's elrs lease stopped (the daemon must not hold the device):
cd /rfnm/apps/elrs && systemctl stop rfnm-elrs
set -a; . ./secret.env; set +a          # ELRS_BINDING_PHRASE (without it the TEST-UID is used, with a warning)
./elrsd --tx-only 20 --tx 1 --rate 250hz --fc 2441.4e6      # --fs 50e6 allowed (no duplex); --tx-only-dbm N
```

All four TX gates apply unchanged (`board.conf TX_ALLOWED`, `--tx 1`, the runtime cap, the adapter);
`--rate auto` and an invalid duration are refused before any device access, each with exit 2 and
`pos_placed:0` in the refusal JSON. Prints one JSON report and exits **0 when `pos_placed > 0`** (the
success criterion — samples at the DAC — reported first, right after `ok`), 1 when nothing reached
the DAC or the transmitter stopped with an error, 2 when refused. Since there is no RX to dump, the
report carries the **planned send channels** instead: `planned_slots` for the first 20 slots
(`slot`, `fhss_ptr`, `channel`, `freq_hz` = nominal channel centre, `freq_air_hz` = the SX1280-exact
transmitted centre, `sync`, `in_rx_window`) plus `freq_lo_hz` and `rx_window`, so the receiving board
knows where to look. It also carries the full TX side (path, applied power, range, LO, sent/dropped/
syncs/retunes, `slots_in_rx_window`, the complete `tx_health`). Progress goes to stderr every 5 s;
SIGINT stops early (TX RF_OFF). The flow (immediate session, bursts placed, SYNC, disarm, and every
gate refusal) is host-tested in `--selftest` (tx section, `selftest_tx_only`); the device sequence
itself is not exercised on the host — `./elrsd --tx-only 5 --tx 1` on the host answers `no device`
with exit 2.

## Build / test

```sh
make                       # host build, no librfnm needed
./elrsd --selftest         # codec vectors, link model, RX chain, TX synth + loopback, daemon glue
./elrsd --loopback         # TX synth -> own RX chain -> decode, 12 dwells at the configured rate
./elrsd --bench 2          # RX chain CPU proxy on a synthetic 25 MSps stream
./elrsd --selfloop-device 20 --tx 1   # board only: TX -> chip loopback -> RX on one device (see above)
./elrsd --tx-only 20 --tx 1            # board only: PURE TX, no RX path (two-board send half, see above)
```

Replay of a cs16 capture (int16 LE interleaved) with the freerun ground truth when the
phrase is exported in the environment:

```sh
./elrsd --replay capture.cs16 --fs 25e6 --fc 2415e6 --rate 250hz --expect-min 1000
```

prints one JSON report (bursts, found, decoded, crc_ok, truth_match, lock, IQ sign used,
realtime factor) and exits 1 when `crc_ok` is below `--expect-min`. `--rate auto` lets the
rate follow the burst duration (replay/scan); `--conj 0|1` pins the IQ sign, otherwise the
first 2 s are probed in both signs.
`--packet-log FILE` additionally writes every decoded packet (the `/packets` entry schema,
one JSON object per line) for external cross-checks. Rate names accept `250hz` or `250`.

Board build: cross-compile aarch64 with `WITH_RFNM=1 ARCHFLAGS=-mcpu=cortex-a53` against a
board sysroot (asio headers + librfnm v2 >= 0.2.1); `make clean` first so no host objects
end up in the link. `-fcx-limited-range` is load-bearing (see Makefile). Easy path:
`./rfnm-sdk build apps` from [github.com/rfnm/sdk](https://github.com/rfnm/sdk).

The Makefile prunes sources whose `// NEEDS:` modules are missing, so a partially
populated tree still builds and reports the absent module selftests as `[SKIP]`

## Run

Deploys to `/rfnm/apps/elrs/` (`elrsd`, `app.json`, `daemon/rfnm-elrs.service`,
`daemon/elrs.conf`) and runs as the systemd unit `rfnm-elrs`, started by appd — never
enabled. It is an RX radio app (`radio:"rx"`): appd holds the lease and starts it;
antenna/gain come from appd's per-app `/rf` settings (`ELRS_ANTENNA`, `ELRS_GAIN`,
`ELRS_AGC`), rate and window from the manifest config keys (`ELRS_RATE`, `ELRS_FC`).
Config precedence is argv > `ELRS_*` env > defaults; bad values warn and fall back to the
default rather than crash-looping. Panel: `webgui/www/app_elrs.js` plus the manifest copy
under `webgui/daemon/manifests/`, one `<script src="app_elrs.js?v=app1">` line before
`apps.js` in the GUI's `index.html`.

## Evidence (host x86, 2026-09-14)

- `make clean && make && ./elrsd --selftest` → `SELFTEST OK`, 384 checks (rx 54, tx 121,
  daemon 49 + codec/link), 24 s build. The 11 new tx checks cover the self-loop verifier
  (pattern, 256-nonce RC byte-equality, SYNC timeline pairs for hop 4 and hop 2, counting,
  JSON, hex parsing) and the adapter's `power_range.min > cap` refusal.
- `--selfloop-device` on the host: `no device` (exit 2) with policy all + `--tx 1`; policy
  none / missing `--tx 1` / `--rate auto` / invalid seconds each refused with exit 2 before any
  device access. Cross build (`make cross APPS=elrsd`, sysroot blue126) → aarch64 ELF, 0
  warnings; not run on a board.
- `--loopback` (TX synth → RX chain → tracker → codec, 12 dwells): 250 Hz 10/12 in-window
  bursts decoded (the first two fall into the envelope warm-up), 500/150/50 Hz 12/12, 12/12,
  6/6 — CRC and ground truth 100 %, FULL lock from the synthesized SYNC packet.
- `--replay` of the 15 s SF6/250 Hz freerun capture (fc 2415 MHz, channels 3..26, phrase from
  the environment): 1305 bursts, 1185 frames found, **1182 CRC-ok, ground truth 1182/1182**,
  one `mod_hop` lock from t = 0.34 s to the end, LQ 100 %, 2.2 s wall (6.9× realtime).
  Python reference on the same file: 1123/1181. The other captures pass their thresholds:
  SF5 2935 CRC-ok (≥ 500), SF7 916 (≥ 780), SF8 498 (≥ 230).
- The replay driver removes the capture's DC offset in front of the chain (mean I 13.6 k,
  Q −3.3 k against a signal std of 3.2 k) — without it the int16 envelope never fires. The
  live chain needs the same stage (open item for the RX front end).
- Not exercised here: the librfnm adapters (`capture_rfnm.cpp`, `tx_rfnm.cpp`) against a
  device, the A53 CPU budget, the board-local IQ sign. No over-the-air transmission.
